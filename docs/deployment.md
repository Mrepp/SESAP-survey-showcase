# Deployment and rollback

The [CI workflow](../.github/workflows/ci.yml) runs on pushes to `staging` and `main` and on PRs to `main`; the [deploy workflow](../.github/workflows/deploy.yml) runs on pushes to `staging` and `main`. A feature branch push does not deploy. The workflow files, not this page, define the exact steps. Review a commit on staging before promoting that reviewed code to `main`. This branch's five worker workflow changes still require a staging run; they are not evidence of a live intake deployment.

Deploy runs processing, then indexing, then admin, showcase, and intake in a matrix, followed by smoke. The admin and intake UIs and showcase UI are built before their workers deploy. Smoke is read only; a passing run proves reachable endpoints and assets, not the contributor journey or authorization rules. A failed smoke run does not automatically roll back.

GitHub Actions `staging` and `production` environments own the deployment secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `KV_NAMESPACE_ID`, `KV_PREVIEW_ID`, and `R2_BUCKET_NAME`. Their variables include `WORKERS_AI_DAILY_NEURON_BUDGET`, `SHOWCASE_URL`, `PROCESSING_URL`, `INDEXING_URL`, optional `ADMIN_URL`, admin `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`, and intake `INTAKE_URL`, `EMAIL_FROM`, and `TURNSTILE_SITE_KEY`. See the workflow and each worker's `wrangler.example.toml` for exact uses. Keep staging and production storage, queues, and credentials separate; the existing workflow has not been validated for that isolation.

The templates use the same worker names in both environments. If both environments target one Cloudflare account, one branch can replace the other's worker. Use separate accounts or change and verify every worker name, service binding, queue, and Durable Object reference before deploying both branches. This isolation decision is still open.

Before staging or production intake can accept submissions, configure its Cloudflare Email sending domain and `EMAIL` binding, an appropriate Turnstile key pair, and the worker secrets `INTAKE_SESSION_SECRET` and `TURNSTILE_SECRET_KEY`. Processing needs `PROCESSING_SHARED_SECRET`; admin needs its Cloudflare Access team domain and audience. Confirm the intended domain layout, DNS, HTTPS, Access policy, email sender, queue resources, and per environment bindings with the project partner and SESAP teammates. Their values remain unconfirmed. Put values in environment configuration and secrets, not prose. The current workflow fills intake public variables but does not create its secrets or external Cloudflare resources.

After deploying staging, check the workflow result, then run [smoke](../tests/smoke/README.md) and the [partner verification script](partner-verification.md) with test material. Record the commit SHA, environment, smoke result, sample record ID, and any finding. Promote only the reviewed commit through the agreed branch review path. Do not invite contributors while [consent text](../packages/core/src/consent/consent-text.ts) is marked draft or the partner has not approved forms and destinations.

For rollback, identify the last accepted commit and its configuration, restore that code through the controlled `staging` or `main` branch path, and watch the deploy and smoke jobs. Check public assets, contributor links, queues, and admin access after rollback. A code rollback does not undo KV/R2 writes, sent emails, or a public build made by a newer version; decide whether records or build artifacts need a separate correction and record that decision. No automatic rollback is implemented.
